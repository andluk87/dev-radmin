# Результаты анализа Radmin VPN 2.1.4951.1

Актуальные последующие результаты: [SRP](srp-findings.md) и
[CChannel / RSession](channel-findings.md),
[начальная цепочка RSA → SRP](bootstrap-findings.md). Разделы ниже описывают первоначальный
статический анализ; позднее код `shelper.dll` исполнялся в ограниченном эмуляторе.

## Что проверено

Шесть частей `Radmin_VPN_2.1.4951.1.zip.001`–`.006` объединены по порядку.
ZIP прошёл CRC-проверку. Извлечён установщик размером 54 277 224 байта:

```text
SHA-256 e16711e2e3e59f6603f51f437197215b1914a3d8316e1f633260178b959921f7
```

Обнаружена строка Inno Setup 6.5.2 и встроенный MSI/OLE по смещению `0xe2c14`
(928788). Через потоки OLE извлечён CAB размером 49 941 657 байт; cabextract 1.11
успешно распаковал его. libarchive 3 отверг этот CAB, поэтому его ошибка сама по себе
не была принята за доказательство повреждения. ZIP CRC проверяет целостность архива,
но не подлинность издателя. Authenticode-проверка доверия и отзыва не выполнялась.
На этапе этого статического анализа установщик и исследуемые DLL/EXE не запускались.

Основные компоненты: служба `RvControlSvc.exe`, библиотека `RvROLClient.dll`,
библиотека `shelper.dll`, `RvUESClient.dll`, интерфейс `RvRvpnGui.exe` и драйверы
виртуального адаптера. Исследованные основные PE-файлы — x86 Windows.
Точные хеши, импорты, экспорты и ссылки: [evidence.json](evidence.json).

Все адреса ниже — VA при предпочтительной базе конкретного бинарника,
а не адреса после ASLR. Это данные только этой сборки.

## Конфигурация подключения

В `RvControlSvc.exe` найдена строка реестра
`SOFTWARE\Famatech\RadminVPN\1.0` и путь открытия HKLM (`0x46a6a0`).
В функции загрузки настроек `0x469c80` читается `ServerAddress`:

| Наблюдение | Адрес/ссылка |
| --- | --- |
| Строка `ServerAddress` | `0x51fcdc` |
| Вызов чтения значения | `0x469f48 -> 0x476000` |
| Проверка строковых типов реестра | `0x4760b1`: типы 1, 7, 2 (REG_SZ, REG_MULTI_SZ, REG_EXPAND_SZ) |
| Передача прочитанной строки | `0x469f5a -> 0x46b790` |
| Сохранение `ServerAddress` | `0x46b826`, далее `0x476720` |
| Строка `FailServers` | `0x51fbf8`; чтение `0x46a483 -> 0x475d00` |
| Строка `ProxyServers` | `0x51fc10`; чтение `0x46a4c0 -> 0x475d00` |
| Встроенные имена | `fail.radminte.com`, `proxy.radminte.com` в `0x46a460` |

Это подтверждает наличие пути настройки адреса без бинарного патча. Но формат
адреса, его приоритет относительно сохранённых серверов и возможность завершить
соединение с собственным сервером ещё не проверены. Registry view и тип фактического
значения позднее подтверждены Windows-отчётом ниже. Типы 1/7/2 перечислены общим строковым reader, это не означает, что
каждый формат подходит для ServerAddress. FailServers/ProxyServers читаются другим
reader: на этапе статического анализа их формат не был установлен. Windows-отчёт
ниже подтвердил MultiString; записывать их как произвольные строки нельзя.

`Registration` в функции загрузки — отдельный подключ реестра для регистрации/
работы с правами; его наличие не доказывает, что ServerAddress хранится в этом подключе.
Диагностика не экспортирует содержимое Registration и ServerPassword.

## Протокол

Служба импортирует `ROLClient_InitDll`, `ROLClient_Register`, `ROLClient_ListenVpn`,
`ROLClient_Connect`, `ROLClient_JoinNetwork`, `ROLClient_ManageNetwork2` и другие
функции из `RvROLClient.dll`. В библиотеке присутствуют RTTI-классы:

- `CRosProtocol_GetROS` — отдельная стадия поиска/получения ROS по названию класса;
- `CRosProtocol_SRP` и варианты `_Register`, `_Attach`, `_Connect`, `_ManageNetwork`;
- пакеты `CRosPktRegistered`, `CRosPktLoginComplete`, `CRosPktRedirect`,
  `CRosPktNetworks`, `CRosPktNetworksChanges`, `CRosPktHeartbeat`, `CRosPktNewConnection`;
- классы и сообщения с NAT, UDP/ENet, TCP и relay в именах.

Имена указывают на архитектуру, но не определяют формат пакетов и поля.
По ним нельзя объявить совместимым JSON/HTTP или произвольный TCP-сервис.

Найдены vtable и код следующих классов:

| Класс/функция | Адрес |
| --- | --- |
| `CRosProtocol_GetROS` основная vtable | `0x10118e64` |
| `CRosProtocol_GetROS` вторичная vtable | `0x10118ee0` |
| Один из обработчиков GetROS | `0x1008ecc0` |
| `CRosProtocol_SRP` основная vtable | `0x10118f44` |
| Обработчики SRP | `0x1008f480`, `0x1008f550`, `0x1008f660` |
| `CRosProtocol_SRP_Register` основная vtable | `0x101193fc` |
| `SHelper_GetNetworkProtocolVersion` | `shelper.dll:0x1006b1d0` |

Последняя функция состоит из `mov eax, 3; ret`: helper сообщает версию протокола 3.
Это версия helper, не доказанная версия всего ROS wire-протокола.
`shelper.dll` экспортирует клиентские и серверные SRP/session/channel/RSA API.
В серверной реализации пока не воспроизведены их ABI, сериализация,
производные ключи и подтверждение аутентификации. Проверки аутентификации и
подписей не отключались.

## Docker и ограничения проверки

Подготовлен собственный диагностический сервис на Go без внешних Go-зависимостей.
Он наблюдает первые байты TCP/UDP, не отвечает на протокол и не проксирует трафик.
Порт стенда 4899 выбран произвольно. В контейнер не включены DLL клиента.

Без Windows-службы с виртуальным сетевым драйвером Linux-контейнер не воспроизводит
настоящий клиент. Wine не установлен; даже его наличие не подтверждало бы работу
Windows-драйвера. Поэтому дальнейшее подтверждение начального обмена требует
тестового Windows-компьютера. Пользователь подтвердил его наличие; подготовлен
read-only скрипт `windows/Get-RadminDiagnostics.ps1`.

Версии/хеши установленного клиента и фактический управляющий TCP-порт позднее
получены в отчёте ниже. Запись начального обмена также получена и разобрана:
[capture-findings.md](capture-findings.md) содержит подтверждённый framing и длины рамок.
Далее можно установить framing, проверить перенаправление на стенд и последовательно
реализовать регистрацию, проверяемый SRP-обмен, управление сетью и передачу пакетов.
До этих проверок совместимость с Radmin VPN не заявляется.

## Проверка по Windows-отчёту пользователя

Получен 30-секундный отчёт с Windows 10 build 19045 / PowerShell 5.1.
Все пять основных модулей совпадают с evidence.json по SHA-256. Для них Windows
сообщила `SignatureStatus=Valid`. Служба `RvControlSvc` находится в Running.
Это показания пользовательской Windows-системы; Linux-проверка Authenticode не выполнялась.

В Registry32 у корневого `SOFTWARE\Famatech\RadminVPN\1.0` обнаружены:
`ServerAddress` типа String, `FailServers` и `ProxyServers` типа MultiString.
Наблюдалось Established-соединение к адресу ServerAddress по TCP/17301.
Таким образом, адрес/тип реестра и используемый управляющий порт теперь подтверждены
runtime-отчётом. Параметр ServerAddress не менялся и перенаправление не проверено.

Фактические IP-адреса, локальные адреса, VPN-IP, PID и исходный пользовательский
отчёт не публикуются в репозитории. Для записи начального обмена добавлен
windows/Capture-RadminControl.ps1 на базе встроенного netsh trace.
Пользователь выполнил его на Windows и прислал пригодный ETL; исправления ошибки
обработки stop и фильтра описаны в [capture-findings.md](capture-findings.md).

## Выполненные проверки реализации стенда

- Три Go-теста прошли: фрагментированный TCP-префикс, тайм-аут с частичным
  сообщением, EOF на настоящем TCP-сокете.
- `go vet ./cmd/probe`, проверка shell-синтаксиса и Python-компиляция прошли.
- `scripts/build.sh` выполнен целиком: тесты, статическая сборка, Docker build.
- Docker healthcheck успешен; интеграционный тест отправил собственные тестовые
  сообщения по TCP и UDP через опубликованные порты и проверил лимит 64 байта,
  результат усечения UDP и отсутствие протокольного ответа.
- Get-RadminDiagnostics.ps1 позднее выполнен пользователем на Windows и подтвердил
  версии/хеши/настройки. Скрипт захвата ещё не проверен на Windows; VPN-трафик пока
  не проверен. Синтетические сообщения не являются тестом совместимости.
