# Встроенный RSA-ключ и переход после SRP

## Встроенные параметры ключа

В исходной `RvControlSvc.exe` версии 2.1.4951.1 найден публичный RSA-ключ:

* SHA-256 EXE: `546efad9ab3ff85c2a50d61524d754bec94a3f3e30d6ae8addef481a1e8daa1e`.
* Блок по VA `0x51f948`, RVA `0x11f948`, длина 212 байт.
* Формат поля: uint32 BE длины, uint32 BE тега, затем значение.
* Тег `0x0a000257`: модуль, 193 байта, включая ведущий ноль, 1536 значащих бит.
* Тег `0x0a000258`: экспонента `01 00 01`, 3 байта, значение 65537.
* `0x46aac0` загружает блок; `0x46aae4`–`0x46aaf1` передаёт указатель и размер.

В `RvROLClient.dll` профиль читает вложенный блок `0x1275` и эти два тега
(`0x1001a917`–`0x1001a95f`), сохраняя буферы в объекте `+0xf0` и `+0xf8`.
Геттер `0x1001a480` возвращает этот набор. Вызов CSRPClient::Start по
`0x1008f423` передаёт набор в цепочку RSession, ранее описанную в
[bootstrap-findings.md](bootstrap-findings.md).
Наличие этого встроенного значения не исключает других профилей или обновления
параметров; все пути выбора настроек приложения пока не восстановлены.

Скрипт `research/client_key.py` проверяет точный хеш исходного EXE, читает блок и
может создать **новую офлайн-копию** с собственным публичным ключом того же размера.
Он меняет только блок публичного ключа и PE checksum. Исходный файл сохраняется;
существующие выходные файлы не перезаписываются. Коды проверки аутентификации и
подписей остаются побайтово прежними. Служба не останавливается, файл не
устанавливается и не запускается.

Изменение публичного ключа делает Authenticode-подпись изготовителя недействительной.
Поэтому копия пока не предназначена для подмены установленной службы. Требования
приложения к подписи/доверенной сборке и работоспособность такого EXE на Windows
ещё не проверены. Обход этих проверок не реализован.

## Проверить офлайн

Использовать оригинальный EXE из собственного установщика, pefile и cryptography
(версии в `research/rsession-requirements.txt`). Установщик и копия EXE в Git не
публикуются.

```bash
# Только анализ, без создания копии:
python research/client_key.py --exe /path/to/RvControlSvc.exe \
  --report /tmp/original-client-key.json
# Для исследования копии, с публичной частью собственного лабораторного ключа:
python research/client_key.py --exe /path/to/RvControlSvc.exe \
  --replacement-public-key /path/to/lab-rsa-public.pem \
  --output /tmp/RvControlSvc-own-key-research.exe \
  --report /tmp/client-key-copy.json
```

Проверено: исходник не изменился; исполняемые секции совпадают; checksum PE верен;
модуль/экспонента соответствуют собственному ключу. Исходная helper-DLL приняла
точно такое 193/3-байтовое представление параметров и создала RSA-запрос 192 байта,
который расшифровывается собственным приватным ключом в ожидаемые 76 байт.
[Краткий отчёт](client-key-validation.json) содержит только результаты, без ключей.
Запуска или проверки подписи изменённого EXE на Windows не было.

## Смена ключа после SRP

После успешного SRP клиент получает 40-байтовый ключ (`0x100969de`, обёртка
`0x100dd330`). По `0x10096a16` он вызывает `0x100df470`, которая обновляет ключи
дешифрования (`0x100df3d0`) и шифрования (`0x100df330`), используя первые 32 байта.

Оригинальные `SHelper_CChannel_SetKeyEnc/SetKeyDec` обновляют расписания AES,
сохраняя оба состояния CBC. Следующее сообщение использует последние блоки
предыдущих сообщений своего направления, а не нулевой IV.

В `internal/channel` добавлен `Rekey` с сохранением цепочек. После исходных
26 native-векторов проверено ещё шесть сообщений с новым ключом, в обоих
направлениях. Побайтовое совпадение Go с DLL подтверждено. Отказавший контекст
не может восстановиться через смену ключа.

Следующий реальный тест — [самостоятельная проверка DLL на Windows](windows-native-check.md).
Она работает с неизменённой DLL и не требует запускать изменённую службу.
Разбор команд управления после аутентификации остаётся незавершённым.
