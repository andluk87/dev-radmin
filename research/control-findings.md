# Управляющие сообщения после SRP

`internal/control` реализует TLV, запросы, ответы Error, IsAlive и кодеки
JoinNetwork/ManageNetwork. Проверка использует исходные инструкции
`RvROLClient.dll` версии 2.1.4951.1, закреплённой SHA-256 в `evidence.json`.
Полный VPN-сервер пока не реализован.

## Сетевой формат и исправление прежнего вывода

Поле: `uint32 BE длины значения`, `uint32 BE тега`, затем значение. Длина
исключает 8-байтовый заголовок; нулевая длина отвергается исходным reader.
Uint32 и uint64 записываются BE.

`0x1232`, `0x124f`, `0x1254` — внутренние логические теги контекстов,
**не внешние обёртки в сетевом сообщении**. Исходный виртуальный сериализатор
`0x10016770 → 0x100a7350 → 0x100a6180` возвращает тело контекста напрямую.
Ранее предполагавшаяся обёртка `0x1232` удалена из Go-декодера.
Входящий диспетчер `0x10089ca0` аналогично задаёт логический корень `0x124f`
при создании parser view поверх уже расшифрованного тела.

Минимальное синтетическое тело запроса команды 20:

```text
00000004 0100031f 00000014
```

Полное приложение добавляет дополнительные поля. Три их варианта (режимы 4/5/9)
получены исходным конструктором `0x10017ec0`, setters, finalizer и сериализатором.

| Поле | Представление | Исходный setter |
| --- | --- | --- |
| `0100031f` | команда uint32 BE, здесь 20 | `100165c0` |
| `1286` | непрозрачный буфер | `10017f30` |
| `122f` | непрозрачный буфер | `10017f80` |
| `1319` | непрозрачный буфер, режим 9 | `10017fb0` |
| `1331` | непрозрачный буфер, режим 4/11 | `10018010` |
| `0b000342` | uint32 BE флага, режим 4 | `10017fe0` |
| `010003e0` | uint32 BE | `10018050` |
| `01000343` | uint32 BE, режим 4/5 | `10018090` |
| `0200030b` | повторяемый uint64 BE, режим 5 | `100180f0` |

Назначение непрозрачных буферов не выводится из их расположения. Тесты используют
синтетические данные. Динамически проверяется построение сообщения, а не весь
путь регистрации/входа Windows-приложения.

## Ответы и keepalive

Фабрика `0x1008a790` читает тип пакета из `01000320` и вызывает исходный decoder.
Для Error (тип 16) обязательны вложенный `123b` и uint32 BE `010001d2` с кодом.
Отсутствующая необязательная строка допустима. `EncodeError(code)` воспроизводит
этот формат. Числовые значения ошибок не получают выдуманных названий.

IsAlive: тип 18, вложенный `1267` с uint64 BE `02000232` (nonce). Ответ клиента
содержит `123c`, внутри которого находятся **оба** элемента: uint32 BE
`010001d4=27` и вложенный `1267` с тем же nonce. Исходный сериализатор `0x10088e90`
подтвердил эту вложенность и совпадение Go побайтно.

Нативно проверены не только выбранные декодеры, но и полный выбор типа фабрикой
для Error и IsAlive. Минимальный LoginComplete75 без списков адресов отвергается. Затем исходная
фабрика приняла вариант с двумя списками: `1343`/`0e000370` и `1340`/`0e00036c`;
элементы — UTF-8 с NUL. Добавлен `Encode/DecodeLoginComplete`, с нейтральным
названием поля `Value25B`, поскольку его полная семантика пока не подтверждена.
Режим `-post-auth-login <endpoint>` отправляет этот ответ после команды20,
выполняет один IsAlive и закрывает экспериментальное соединение.
Это подтверждение формата и функций DLL, а не полноценного состояния VPN.

## Запросы работы с сетью

JoinNetwork использует команду 39, вложенный `131c`. Подтверждены:

- имя `03000306`: UTF16BE с завершающими байтами `0001`;
- флаг `0b00033f`: uint32 BE;
- переданное извне proof `0a00030e`: непрозрачные байты;
- параметры `02000340` (uint64), `0100034a`, `010003be` (uint32).

ManageNetwork: команда 52, поле `1319` с переданными вызывающим кодом байтами.
`Encode/DecodeManageRequest` сохраняют их без интерпретации.

Шесть векторов получены исходными конструкторами/setters/сериализаторами,
включая кириллицу в имени. Проверены ветви с переданным синтетическим proof и
пустым материалом пароля. Вычисление proof из реального сетевого пароля,
проверка прав и семантика операций создания/удаления сети не воспроизведены.
Кодеки не объявляют такие операции успешными.

## Воспроизведение и границы проверки

```bash
python research/control_interop.py --dll /path/to/RvROLClient.dll --output /tmp/tlv.json
python research/request_interop.py --dll /path/to/RvROLClient.dll --output /tmp/requests.json
python research/response_interop.py --dll /path/to/RvROLClient.dll --output /tmp/responses.json
python research/network_interop.py --dll /path/to/RvROLClient.dll --output /tmp/networks.json
go test ./internal/control
```

Нужны pefile и Unicorn из `research/interop-requirements.txt`; выходные файлы
должны отсутствовать. Fixtures в `internal/control/testdata` содержат только
синтетические значения. Оригинальные DLL не распространяются.
Нативные вызовы ограничены памятью, временем и числом инструкций. Для фабрик
и сериализаторов моделируются только выделение памяти и необходимые
Get/SetLastError; выбранные простые decoders обходятся без этих моделей.
DLL initialization, Windows-служба и драйвер не запускаются.

Go ограничивает сообщение 1 МиБ и число полей 1024; это пределы стенда,
не установленные пределы исходного приложения. Неизвестные поля сохраняются.
Дубликаты обязательных полей отвергаются по собственной строгой политике;
это не утверждение о поведении DLL на всех неоднозначных сообщениях.

`research/lab_check.py` автоматически запускает локальный TCP-сервер,
генерирует временные собственные ключи/запись и проверяет RSA/SRP, отказы,
смену ключа, управляющие запросы/Error и IsAlive. Флаг `--rol-dll` включает
исходные конструкторы и фабрику. Команда приведена в README. Отчёт сохраняет
только статусы и длины, без ключей, паролей, nonce и содержимого буферов.

Для полной совместимости остаются подтверждённый современный login/registration,
проверка прав сетей, содержимое операций ManageNetwork, доставка peer-состояния,
NAT/relay и VPN data plane. Реальный Windows-тест описан отдельно в
`windows-native-check.md` и пока не получен.

Сохранённый `lab-validation.json`: 28 сквозных TCP-сценариев прошли, включая
команды 20/39/52 с исходными сериализаторами и ответы Error с исходной фабрикой,
отказы на повреждённых сообщениях, IsAlive и неверный nonce. `go test ./...`,
`go vet ./...`, race-проверки сервера/кодеков, кросс-сборка Windows/386 и проверка
SHA-256 собранных бинарников прошли. Docker в этой итерации не запускался.

Дополнительная проверка Docker: `docker-validation.json` содержит 30 прошедших
сквозных сценариев, включая LoginComplete75 и неверный nonce после него.
`research/login_interop.py` воспроизводит исходную фабрику с моделями выделения
памяти и UTF-8/UTF-16 конверсии; fixture — `native-login.json`.
Отдельно проверено соединение с развёрнутым контейнером на публичном ключе,
извлечённом непосредственно из изменённой копии EXE. Сам EXE на Windows не запускался.
