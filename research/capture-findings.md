# Разбор первого ETL-захвата

Исходный ETL успешно прочитан офлайн на Linux с помощью dissect.etl 3.14.
Нативный `etl2pcapng.exe` и Windows для разбора не потребовались.
Пользовательский ETL, отфильтрованный PCAP, IP-адреса и непрозрачные тела сообщений
хранятся вне репозитория и в Git не публикуются.

## Что было с ошибкой stop

Старт трассировки и перезапуск RvControlSvc подтверждены логом/метаданными.
К моменту `netsh trace stop` трассировка уже отсутствовала, что также подтвердил
пользователь отдельными командами. Файл имеет размер 16 МиБ — заданный лимит single-mode;
его заголовок содержит время окончания и 32 записанных буфера.
Это согласуется с автоматическим окончанием по лимиту, но отдельного события с
доказанной причиной остановки мы не получили. Ненулевой код stop сам по себе
не означает, что пакеты не сохранились. Проверка старого скрипта была ошибочной.

В загруженной справке Windows явно указано: один лишь `IPv4.Address` не исключает
другие Ethernet-типы. Поэтому исходный фильтр пропустил IPv6/ARP/LLDP.
Новая версия Capture-RadminControl.ps1 явно задаёт `Ethernet.Type=IPv4` и `Protocol=TCP`.
Также она сохраняет StopExitCode и пытается преобразовать существующий ETL даже при
ненулевом stop. При этом TraceStopped остаётся false: успешная остановка скриптом
не выдумывается. Изменённый вариант требует отдельной Windows-проверки;
повторный захват для текущего разбора не требуется.

## Реально извлечённые данные

- 131 924 ETW-события, из них 1 144 события NDIS PacketCapture.
- 118 наблюдений выбранного IPv4 TCP-потока; после удаления 59 точных повторов
  остаётся 59 наблюдений. Повторы согласуются с захватом на нескольких слоях,
  но не доказывают наличие/отсутствие сетевых ретрансляций.
- Три TCP-соединения: одно закрывавшееся без данных и два новых с SYN/SYN-ACK.
- В четырёх направлениях двух новых соединений восстановленные данные непрерывны:
  пропусков и конфликтующих перекрытий не обнаружено. Это утверждение о захваченном
  интервале, а не обо всём времени жизни соединений.
- Разбиение на рамки полностью исчерпывает эти четыре восстановленных потока;
  неполных хвостов и превышения лимитов анализатора нет.

## Подтверждённое framing

На TCP/17301 каждая наблюдённая рамка имеет четырёхбайтовый префикс длины тела
в big-endian. Длина не включает сам префикс.
Первое сообщение клиента и сервера в обоих новых соединениях:

```text
00 00 00 04 | 03 00 00 00
  длина=4  | значение 3 в little-endian
```

Это совпадает с результатом статического разбора SHelper_GetNetworkProtocolVersion.
Остальные тела здесь не интерпретируются и не публикуются.

| Соединение | Направление | Наблюдённые длины тел рамок, байт |
| --- | --- | --- |
| Новое A | клиент → сервер | 4, 192, 32, 224, 48, 288, 112 |
| Новое A | сервер → клиент | 4, 256, 224, 48, 1968, 96, 5072 |
| Новое B | клиент → сервер | 4, 192, 32, 224, 48, 192, 480, 528 |
| Новое B | сервер → клиент | 4, 256, 224, 48, 1936, 160, 384, 288, 384 |

Начало обмена в A: клиент прислал тело 4, затем 192; сервер ответил телом 4;
клиент прислал 32; сервер ответил 256; далее клиент/сервер обменялись телами 224
и затем 48. Определять эти поля как конкретные ключи, salt или proof только по
длинам нельзя. Последующие большие рамки пересекают границы TCP-пакетов, поэтому
нужна сборка TCP-потока, а не трактовка каждого пакета как отдельного сообщения.

## Код и проверки

Добавлены internal/wire с bounded reader/writer и research/analyze_etl.py с:
выбором только указанного управляющего потока, сортировкой времени ETW,
удалением точных TCP-повторов, сборкой по sequence numbers, обнаружением пропусков
и конфликтующих перекрытий. Анализатор намеренно поддерживает только одиночные
Ethernet NDIS PacketFragment-события Windows 8.1+; неподдержанные типы считаются
отдельно. Опциональный PCAP содержит только выбранный поток и остаётся частным.

Шесть Go-тестов (три существующих теста probe и три новых wire) и шесть Python-тестов
прошли, go vet прошёл. Тестовые тела синтетические: пользовательские криптографические
сообщения в тесты не скопированы. Реальный ETL отдельно обработан целиком.

Рамки, версия и размеры подтверждены. Алгоритмы handshake, производные ключи,
проверка аутентификации, регистрация/управление сетями и VPN data plane пока
не воспроизведены. Существующий Docker probe не стал совместимым VPN-сервером.
