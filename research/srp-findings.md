# Внутренний SRP: реализация и воспроизведение

Реализована серверная сторона **внутреннего** обмена `shelper.dll` на Go:
`internal/srp` и `cmd/srp-lab`. Это отдельный подтверждённый этап, а не полный
управляющий сервер Radmin VPN. Оболочка захваченного TCP-обмена, управление сетями
и передача VPN-трафика ещё не реализованы. Перенаправлять Windows-клиент на этот
порт пока рано.

## Как проверено

Исходный x86-код DLL исполняется через Unicorn с ограниченной моделью WinAPI
(`helper_runtime.py`). SHA-256 DLL строго проверяется:
`d89daf6bcd5cafa3c7f6173f835ccf045baf8e7134f868819db6fd7615959ac4`.
Двоичный файл не изменяется. Модель предоставляет память, однопоточные блокировки,
CP1252 и случайные байты через Python `secrets`; неизвестные вызовы останавливают
эксперимент. Есть ограничения памяти, времени и количества инструкций.
Эмулятор не является Windows, проверкой GUI или защитной песочницей общего назначения.

Выполнены три сценария DLL-клиент → DLL-сервер и три DLL-клиент → Go-сервер:
правильный пароль, неверный пароль, повреждённое подтверждение M1. Первый сценарий
завершает взаимную аутентификацию, два остальных отклоняются на этапе подтверждения.
Для DLL → DLL дополнительно сравниваются 40-байтовые ключи. Эти же три сценария
проверяются через TCP и Docker с настоящим эмулируемым клиентским кодом DLL.
Все данные тестов синтетические; ключи сессий не записываются в отчёт.

Особенность DLL: `GetKey` может вернуть производный ключ до проверки подтверждения
и после отказа. Наш `SessionKey` выдаёт ключ только после успешного M1.

## Параметры

* Нестандартный модуль N: 1536 бит, точное значение в `internal/srp/srp.go`, g = 5.
* H = SHA-1; соль 32 байта. I — uint64 LE с перестановкой байтов внутри каждого
  16-битного слова: для 42 это `002a000000000000`.
* x = H(salt || H(I || ":" || password)), v = g^x mod N.
* k = H(N || PAD(g,192)), u = H(PAD(A,192) || PAD(B,192)).
* B = (k*v + g^b) mod N; S = (A*v^u mod N)^b mod N.
* K = H(Sminimal || uint32BE(0)) || H(Sminimal || uint32BE(1)), то есть MGF1,
  40 байт. S представлен минимальным big-endian числом.
* M1 = H((H(N) xor H(gminimal)) || H(I) || salt || Araw || Braw || K).
* M2 = H(Araw || M1 || K).

Это совместимость с устаревшим алгоритмом; `math/big` не обеспечивает постоянное
время операций. Лабораторный код не предназначен для промышленной аутентификации.
Три вектора verifier в `internal/srp/testdata/native-verifiers.json` получены
исходной DLL, пароль в них намеренно публичный тестовый.

TLV-заголовок — uint32 BE: тип `header & 0xf8000000`, длина
`header & 0x07ffffff`. Поле состояния имеет тип `0x10000000` и uint32 BE.

| Направление | Состояние | Дополнительные поля | Типичная длина тела |
|---|---:|---|---:|
| Клиент → сервер | 1 | `0x20000000`: id, uint64 LE | 20 |
| Сервер → клиент | 2 | `0x30000000`: N, `0x40000000`: g, `0x50000000`: соль | 245 |
| Клиент → сервер | 3 | `0x60000000`: A | 204 |
| Сервер → клиент | 4 | `0x60000000`: B | 204 |
| Клиент → сервер | 5 | `0x70000000`: M1 | 32 |
| Сервер → клиент | 6 | `0x70000000`: M2 | 32 |

Лабораторный TCP-сервис оборачивает каждое тело в uint32 BE длины.
Это транспорт для проверки внутреннего API; соответствие внешнему обмену
реального приложения этим не устанавливается.

## Воспроизвести на Linux amd64

Нужен собственный извлечённый `shelper.dll` указанной версии и Python 3.
Установщик и DLL в Git не распространяются.

```bash
python3 -m venv .venv
.venv/bin/pip install -r research/interop-requirements.txt
.venv/bin/python research/fetch_codepage.py /tmp/radmin-bestfit1252.txt
sha256sum -c bin/srp-lab.sha256
.venv/bin/python research/native_interop.py \
  --dll /path/to/shelper.dll --mapping /tmp/radmin-bestfit1252.txt \
  --server-bin ./bin/srp-lab --output /tmp/radmin-interop.json \
  --write-lab-record ./lab-record.json
```

Выходные файлы должны ещё не существовать. `lab-record.json` содержит verifier
для публичного тестового пароля; используется только для локальных экспериментов.
Go не нужен для запуска готового Linux amd64 бинарного файла. Для пересборки:
`GO_BINARY=/path/to/go bash scripts/build.sh` (Go 1.22+, Docker Compose).

Затем запустить Docker-профиль и повторить тест через контейнер:

```bash
# Только синтетическая запись с публичным паролем; UID 65532 должен иметь доступ.
chmod 0444 lab-record.json
SRP_LAB_RECORD="$PWD/lab-record.json" \
  docker compose -p dev-radmin-research --profile srp-lab up --build -d srp-lab
.venv/bin/python research/native_interop.py \
  --dll /path/to/shelper.dll --mapping /tmp/radmin-bestfit1252.txt \
  --server-address 127.0.0.1:17302 --output /tmp/radmin-docker-interop.json
docker compose -p dev-radmin-research --profile srp-lab logs srp-lab
```

В журнале после `listening` ожидаются `authentication_complete`, затем два
`rejected` с причиной `authentication`. Во внешнем режиме harness проверяет
клиентское завершение/отказ; серверную причину нужно проверить по журналу.
Профиль слушает только localhost:17302, работает без root и без дополнительных
capabilities. Запись не создаётся автоматически; учётной записи по умолчанию нет.
Основной профиль `probe` сохраняет прежнее диагностическое назначение.

Дальнейший этап исследования — внешняя оболочка управляющего обмена и её связь
с внутренним API. Новый захват с пользовательского Windows пока не требуется.
