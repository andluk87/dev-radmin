# Начальная последовательность RSA → CChannel → SRP

Добавлен серверный RSA-этап на Go (`internal/bootstrap`, параметр `-rsa-key` у
`srp-lab`). Через Docker успешно проверена вся цепочка с исходными клиентскими
функциями DLL: версия протокола → RSA key transport → AES-канал → взаимный SRP.
Ключ RSA собственный тестовый; исходный Windows-клиент целиком ещё не проверялся.
Сервер завершает соединение после аутентификации и не реализует команды управления
сетями, регистрацию/базу пользователей или пересылку VPN-пакетов.

## Порядок реального захвата

Дополнительная проверка хронологии TCP-сегментов разрешила неоднозначность
раздельных списков длин в [первом отчёте](capture-findings.md).
Первые сообщения двух новых соединений идут в таком порядке:

| Направление | Длина тела | Воспроизведённый этап |
|---|---:|---|
| Клиент → сервер | 4 | uint32 LE версии 3 |
| Клиент → сервер | 192 | RSA key transport, ключ 1536 бит |
| Сервер → клиент | 4 | ответ RSession, uint32 LE |
| Клиент → сервер | 32 | CChannel: SRP-состояние 1, открытое тело 20 байт |
| Сервер → клиент | 256 | CChannel: SRP-состояние 2, открытое тело 245 байт |
| Клиент → сервер | 224 | CChannel: SRP-состояние 3 |
| Сервер → клиент | 224 | CChannel: SRP-состояние 4 |
| Клиент → сервер | 48 | CChannel: подтверждение M1 |
| Сервер → клиент | 48 | CChannel: подтверждение M2 |

Каждое тело имеет внешний uint32 BE длины. Для первого соединения клиентские
4 и 192 байта наблюдались до первого серверного ответа 4 байта. Поэтому серверная
рамка 256 байт относится уже к следующему этапу, а не является ответом RSA.
Соответствие этапов поддерживается хронологией, статическими вызовами и
воспроизведением той же последовательности длин. Расшифровка пользовательского
захвата не выполнялась: приватного ключа исходного сервера у нас нет.

## Что подтверждено в коде RvROLClient.dll

Адреса относятся к исходной DLL из `research/evidence.json`:

* `0x10096bf0` — последовательность CSRPClient, вызывает RSA-обёртку
  `0x100dcc90`, затем цикл `0x100dcf20`.
* `0x100dccf0` через таблицу функций вызывает `RSession_CreateClient`.
* `0x100dcf20` вызывает `RSession_GetNextBuffer` и возвращает очередной буфер.
* `0x100dce30` получает ключевой материал через `RSession_GetKey`.
* Участок `0x10096f0d`–`0x10096f21` передаёт один и тот же буфер ключа дважды
  в `0x100df250`. Эта функция использует первые 32 байта каждого аргумента
  для создания CChannel. Следовательно, в этой клиентской цепочке оба направления
  получают первые 32 байта 64-байтового RSession-материала. Это не разбиение на
  две половины. IV и состояния CBC при этом отдельные.

Полная `RvROLClient.dll` пока не исполнялась в эмуляторе. Динамически проверены
исходные экспортируемые RSession/CChannel/SRP-функции helper; связь между ними
со стороны RvROL подтверждена статическим анализом.

## Реализация и проверки

Сервер читает рамку версии 3 и RSA-шифротекст, расшифровывает PKCS#1 v1.5 и
требует ровно 76 байт: три uint32 LE и 64 байта материала. Он отвечает рамкой
uint32 LE версии 3, создаёт CChannel и затем проверяет SRP.

Приватный RSA PEM задаётся явно, не включается в образ и не появляется в журнале.
Нет встроенного приватного ключа или учётной записи по умолчанию. Режим
`-channel-record` с фиксированными тестовыми ключами и режим `-rsa-key` исключают
друг друга. Сервис ограничивает длины, время соединения и не выдаёт успешную
аутентификацию до проверки M1.

В Docker прошли четыре сценария с оригинальными DLL-функциями клиента:
успешный пароль; неверный пароль; изменённый M1; изменённая зашифрованная запись.
Отказы различаются в локальном журнале (`authentication` / `channel`). Также
проверены отказ на неверной версии, неправильной длине RSA и неверном заполнении
RSA без выдачи ответа. Go-тесты проверяют границы, обработку ключей, испорченные
сообщения, нативные векторы и защиту состояния после отказа.

Совместимость со старыми RSA/CBC/MD4/SHA-1 нужна только для исследования.
Сервис не является готовым промышленным криптографическим или VPN-сервером.

## Воспроизвести на Linux amd64

Сначала подготовить Python-окружение, собственную `shelper.dll`, CP1252 и
`lab-record.json` по [SRP-инструкции](srp-findings.md). Все тесты используют
публичный синтетический пароль. Далее выполнить обычным Linux-пользователем,
не root; контейнеру задаётся тот же UID, чтобы читать закрытый ключ с правами 0600.

```bash
.venv/bin/pip install -r research/rsession-requirements.txt
# Только для этой лаборатории; ключи ещё не должны существовать.
test ! -e lab-rsa-key.pem && test ! -e lab-rsa-public.pem
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:1536 -out lab-rsa-key.pem
chmod 0600 lab-rsa-key.pem
openssl pkey -in lab-rsa-key.pem -pubout -out lab-rsa-public.pem
sha256sum -c bin/srp-lab.sha256
docker compose --profile srp-lab build srp-lab
SRP_LAB_RECORD="$PWD/lab-record.json" \
  docker compose -p dev-radmin-research --profile srp-lab run \
  --name dev-radmin-bootstrap-lab -d --no-deps \
  --user "$(id -u):$(id -g)" -p 127.0.0.1:17304:17304 \
  -v "$PWD/lab-rsa-key.pem:/run/lab-rsa-key.pem:ro" \
  srp-lab -listen :17304 -record /run/srp-record.json \
  -rsa-key /run/lab-rsa-key.pem
.venv/bin/python research/bootstrap_interop.py \
  --dll /path/to/shelper.dll --mapping /tmp/radmin-bestfit1252.txt \
  --public-key ./lab-rsa-public.pem --server-address 127.0.0.1:17304 \
  --output /tmp/radmin-bootstrap.json
docker logs dev-radmin-bootstrap-lab
# После проверки:
docker rm -f dev-radmin-bootstrap-lab
```

Перед генерацией убедиться, что оба PEM-файла отсутствуют; OpenSSL сам может
перезаписать существующий файл. Отчёт harness также должен иметь новое имя.
Исходные DLL, реальные захваты, закрытые RSA-ключи и записи реальных пользователей
в Git не публикуются.

Следующий незавершённый этап — найти источник параметров RSA/сервера у приложения
и подготовить клиент для собственного ключа с сохранением проверок аутентификации,
затем разобрать команды после SRP. Новый запуск на пользовательском Windows пока
не нужен.
